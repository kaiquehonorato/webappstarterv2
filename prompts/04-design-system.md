# 04 · Design system: tokens, components, platform conventions, motion, app icon
Model: Sonnet · effort medium · new session on your computer (screenshots need the simulators) · raise to high if components miss states or accessibility checks
Start: `claude --model sonnet --effort medium`

The visual direction you picked in Phase 1 becomes real, reusable components with every state, so features never invent their own buttons, sheets or animations. It also produces the app icon and the splash screen, the first two things anyone sees.

```text
Read AGENTS.md, .claude/rules/mobile.md, docs/writing-style.md, and the visual-direction ADR from Phase 1 with its screenshots in docs/manual/img/directions/. This is Phase 4: turn the chosen direction into a design system in packages/ui (or the folder named in docs/architecture.md). One Issue, one branch and one PR per step. Use the frontend-design skill with the Phase 1 ADR as its brief: build that direction, don't propose a new one. The platforms' conventions (Apple's Human Interface Guidelines, Material Design) decide where things go and how they behave; the direction decides how they look. Resize screenshots to 390 px wide and open only those of components you changed.

Step 1. Tokens, as typed exports the app and the site both use. Color roles (background, surface, text, muted, border, primary, accent, success, warning, danger, focus) for light and dark, following the phone's appearance setting, every text pair at 4.5:1 contrast or more (3:1 for large text and UI parts), checked by a test. A type scale that grows with the phone's text size setting (Dynamic Type on iOS, font scale on Android) up to 200%, with a test or screenshot proving the longest labels still fit. Spacing, radius, elevation and z-order. The minimum touch target (44 pt on iOS, 48 dp on Android). Motion: durations around 120, 200 and 300 ms and named easing curves, plus a small set of haptic patterns (selection, success, warning) used only to confirm.

Step 2. Components, each with every state (default, pressed, focused for keyboards and switch control, disabled, loading, error), an accessible name and role for VoiceOver and TalkBack, and the touch target from Step 1: Button (primary, secondary, ghost, danger, icon-only with an accessible name), Text field (label, hint, an error that says how to fix it, the right keyboard and autofill type), Text area, Select or picker (native where people expect it), Checkbox, Radio, Switch, Segmented control, Search field with suggestions, List row and section, Card, Bottom sheet, Dialog and the confirmation for destructive actions (native alert where it fits), Toast or snackbar with an Undo action, Tab bar, Header with back navigation, Badge, Avatar, Empty state (what this place is for and the next action), Error state (what happened, and retry), Offline banner, Skeletons, Pull to refresh, a list with pagination and a loading footer, and the permission explainer screen. Build on the stack's accessible primitives instead of hand-made focus and gesture handling. Icons from one set with a compatible license (e.g. Lucide ISC, Phosphor MIT, Tabler MIT, Material Symbols Apache-2.0; Apple's SF Symbols only inside the iOS app, as Apple's license allows), always with a visible label or an accessible name.

Step 3. Helpful patterns, documented with an example each: inline validation after the first blur; suggestions and autocomplete where they save typing; sensible defaults; undo for reversible actions and a confirmation that names the object for irreversible ones; optimistic updates with rollback; visible progress for anything slower than about one second; what works offline and what the person sees when the connection returns; asking for a permission at the moment of need after a screen that says why, and the path when it is refused; keyboard handling (the field stays visible, "Next" moves on, "Done" submits); sign-in that uses the platform's password and one-time-code autofill.

Step 4. Motion and haptics. Motion explains change: where a screen came from, what was added, what is loading. Use the platform's own navigation transitions, so a push, a sheet and a modal feel native on each; 150–300 ms for UI feedback; transform and opacity only; at most one orchestrated moment per screen. The phone's "reduce motion" setting turns animations into a short crossfade or nothing. Haptics confirm an action the person can also see; they never carry information alone, and they follow the phone's system setting. Use an animation library only when the framework's own tools can't do it, and check its license (GSAP has a custom license: ask me before adding it).

Step 5. Gestures and scrolling. Decide them once here instead of per screen.
- Lists are virtualized and scroll without dropped frames on the slowest phone in the device list; measure it and put the numbers in the PR.
- Pull to refresh where content changes; a header that collapses only where it is the platform's idiom (iOS large titles); sticky section headers when long lists need a sense of place.
- Every gesture has a visible alternative: swipe to delete also exists as a button or menu item; long press is never the only way to reach an action; drag to reorder has buttons for screen reader users.
- Hard limits: the Android back button and gesture and the iOS swipe-back always work and never trap the person; no custom scroll physics; nothing moves while someone is reading; content is complete without any animation.

Step 6. App icon and splash screen. Draw the icon from the direction: one idea, readable at the smallest size, no text, no screenshot of the UI. Produce what each store and OS version asks for: the iOS icon at 1024×1024 without transparency, with the appearance variants (dark, tinted) current iOS versions use; the Android adaptive icon (foreground and background layers) with a monochrome layer for themed icons; the 512×512 Google Play icon. The splash screen is the background color and the icon only, matching the first screen so there is no flash, in light and dark. Record the source files and their license in docs/assets-licenses.md. Never use another brand's marks, and no icon that imitates a well-known app's.

Step 7. A component catalog screen, compiled into development builds only, that shows every component in every state, in light and dark, at the default and the largest text size. Screenshot tests of it on iOS and Android (with the stack's snapshot or end-to-end tool, run where CI or my computer has the simulators), and the token contrast test in the checks CI requires on every PR, as Phase 3 Step 4 says. Review the catalog against the list of generic looks in prompts/01-prototype-manual.md and against docs/writing-style.md, and fix whatever reads as a template.

Licensing: only fonts, icons, images, illustrations, sounds, animations and 3D models whose licenses allow commercial use and embedding in an app, each recorded in docs/assets-licenses.md. Don't copy another company's design or brand.
Gate: screenshots of the catalog on iOS and Android, in light and dark and at the largest text size, plus the app icon on a home screen and the splash screen, in the PR; docs/ROADMAP.md updated; wait for my approval. Then tell me how to start Phase 4b (the pages the stores require), or Phase 5 first if those pages can wait until before launch.
```

**Get a second opinion on the look.** Everything in this phase checks whether the design follows the rules, not whether it is any good. In the terminal or the desktop app, the Anthropic `Design` plugin adds `design-critique` for exactly that, plus `accessibility-review` and `ux-copy`; connect none of its bundled MCP servers (docs/skills-and-plugins.md). Without it, start a fresh session on Opus at medium effort, give it only the catalog screenshots and SPEC.md, and ask what a senior app designer would change first.

**3D and heavy animation:** rarely worth it in an app made of screens and forms. If the Phase 1 direction depends on it, treat it like the web kit does: one moment where it carries meaning, loaded after the first screen, a static fallback under "reduce motion" and on low-end phones, and the startup and size budgets still met.
