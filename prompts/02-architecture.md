# 02 · Architecture and stack: app framework, backend, builds, data model
Model: `opusplan` (Opus while planning, Sonnet while writing the docs) · effort high · plan mode · new session · raise to Opus · xhigh when there are many constraints or the options don't convince you
Start: `claude --model opusplan --effort high --permission-mode plan`

Every choice that is expensive to undo is made here, with you, before any application code exists. For a store app that includes some that can never be undone, such as the app's identifiers, and some that decide what every release costs, such as how builds and updates work.

```text
Read AGENTS.md, SPEC.md, docs/GLOSSARY.md, docs/manual/USE-CASES.md, docs/ROADMAP.md, docs/app-stores.md and the ADRs in docs/adr/. This is Phase 2: decide the architecture with me. Stay in plan mode until I approve the plan. No application code in this phase.

Part A. Decisions we make together. For each one: a short table of 2–3 realistic options, your recommendation with the reason, then ask me. Each accepted decision becomes an ADR in docs/adr/ (use the template). Check versions, prices and store rules in the official documentation, not from memory.
1. How the app is built. Compare what fits SPEC.md: a cross-platform framework (React Native with Expo, TypeScript; or Flutter, Dart), two native apps (Swift and Kotlin), or a web app inside a native shell (Capacitor). Weigh: one codebase or two; whether the language matches the backend, so app and API can share the zod schemas in packages/shared; access to the phone features SPEC.md needs; building iOS apps without a Mac (cloud builds); over-the-air updates; how often the framework needs upgrading and how painful that is; how well Claude and the community know it. A web app in a shell risks rejection under App Review Guideline 4.2 when it is mostly a website, so say whether ours would be. If Phase 0 left the store question open, settle it here.
2. Backend and repository shape. A small monorepo (apps/mobile, apps/api, apps/site for the Phase 4b pages, packages/shared, packages/ui, packages/db), or a backend-as-a-service (Supabase, Firebase) the app talks to directly. With direct access, the key inside the app is public and row-level security is the only protection, so say what that means for every table SPEC.md needs.
3. Database and data access: PostgreSQL unless the spec gives a reason otherwise; an ORM or query builder that is typed and parameterizes queries by default; a migration tool.
4. Hosting for the API, the database, file storage and the site. Compare: monthly cost at launch, at 1,000 and at 10,000 active users (free-tier limits included, and where the price jumps); region and latency for our users (for Ireland, a Dublin or other EU region, with backups kept in the EU too); the backups each plan includes and what more costs (for example, Supabase Free has no automatic backups, Pro keeps 7 days of daily backups, and point-in-time recovery is a paid add-on that also needs a larger compute size), and whether file storage is backed up too; a preview deployment per pull request that requires sign-in, and how an automated scanner gets past it; built-in logs and metrics; lock-in and how we would move away; the provider's data processing agreement (GDPR Art. 28) and, if personal data leaves the EEA, the transfer mechanism it relies on (an adequacy decision such as the EU-US Data Privacy Framework, or standard contractual clauses). Take into account the accounts and plans I already have.
5. Authentication: a proven provider or library, never home-made password or token crypto; sign-in methods that suit the users (e-mail code, passkeys, social sign-in); if we offer Google or another social sign-in on iOS, Apple's Guideline 4.8 also requires an equivalent option that protects privacy, such as Sign in with Apple; how tokens are issued, refreshed, stored on the phone and revoked; MFA for admins; account deletion inside the app.
6. Builds, signing and releases: where builds run (a cloud build service such as EAS Build or Codemagic, GitHub Actions with macOS runners, or Xcode on a Mac with fastlane) and what each costs per month at our pace; who holds the signing keys (the build service's credential store or CI secrets, never the repo or an agent session) and Play App Signing turned on; app variants for development, preview and production, with separate identifiers so they install side by side and never touch production data; how test builds reach testers (TestFlight, Play internal testing, or the private routes in docs/app-stores.md); over-the-air updates or not, through which service, with signed updates and separate channels; the minimum iOS and Android versions, from the users' real phones, not fashion.
7. Phone features and services, only those SPEC.md needs, each with the data it receives and its country: push notifications (APNs and FCM directly, or a service on top); offline (online-only with clear errors, cached reads, or offline writes with a sync queue and a conflict rule); maps and location; camera and uploads; payments (the stores' in-app purchase for digital goods, a payment provider for physical goods and services, and whether a service such as a receipt validator is worth its data); crash reporting and analytics without personal data; the stores' age signals if minors may use the app. Start on free or test tiers.
8. Measuring success: for each success signal in SPEC.md, how we will measure it (an event counted on the server, a database query, or analytics that need no consent and no tracking permission), with no personal data beyond what SPEC.md allows.
Criteria, in this order: fits the spec; accepted by both stores; boring, popular and well documented, so you and I can maintain it; fewest moving parts; secure defaults; cost; compliance.

Part B. Architecture, written to docs/architecture.md with Mermaid diagrams (C4 context and container, including the stores, the build service and the push service, plus a sequence diagram of the most important flow and one of sign-in with token refresh).
- Monorepo by feature: features/<name>/ in the app and in the API, with index.ts as the only public entry point. No microservices.
- API layers, each with one job:
  - Controller (api): route handlers, webhooks, store server notifications and jobs. Parse the request, authenticate, validate with the shared zod schema, call one service method, map the result or error to HTTP. No business rules, no SQL.
  - Service: business rules and use cases. Authorizes the action on this specific record, runs transactions, calls repositories and adapters for external systems. Unit-testable without HTTP or a database.
  - Repository: the only code that talks to the database. Every query is scoped by owner or tenant. Returns domain types, not raw rows.
  - Model and contract: the database schema, domain types, and the zod schemas in packages/shared that app and backend both import.
- App layers: screens and components (no business rules, no direct network calls) → hooks that own loading, error, cache and offline state → a typed API client built from the shared schemas. Navigation map. What is stored on the phone, where (secure storage or not), and when it is cleared (sign-out, account deletion).
- Classes or functions: services, repositories and adapters are classes that receive their dependencies through the constructor, so tests can pass fakes; pure logic stays in plain functions; small value types (Money, EmailAddress) only where they prevent real bugs. No base classes, generic repositories or factories until there are two real uses.
- Errors: typed domain errors (NotFound, Forbidden, Conflict, ValidationFailed, UpdateRequired) mapped to HTTP in one place and to app screens in one place; one JSON shape { error: { code, message } }; no stack traces or SQL in responses.
- Config and logging: server env vars validated at startup; app config fixed at build time and public by definition; structured server logs with a request ID, the app version and platform, and personal data redacted; no personal data in device logs or crash reports.
- Data model: a Mermaid ER diagram; an owner or tenant column on every user-owned table; created and updated audit fields; soft or hard delete per table, with the reason; which columns hold personal data and for how long; indexes for the main queries; money as integer minor units and times in UTC; reversible migrations, with expand → migrate → contract for breaking changes.
- API conventions: resource naming, cursor pagination with a hard maximum page size, filtering, idempotency keys for payments and for writes the app retries after being offline, rate limits per route, and versioning for clients we can't update: changes are additive, a breaking change gets a new version, and every request sends the app version so the API can answer "update required".
- Security architecture: roles plus per-record checks, and where each check runs; the app as an untrusted client; the token lifecycle; secure storage on the phone; deep links on verified domains (the site serves the association files from Phase 4b); WebView policy; whether to pin certificates (it protects against a rogue certificate authority or a proxy, and it locks every user out if a certificate rotates without a plan), and whether the API checks that requests come from a genuine app (App Attest, Play Integrity) for abuse-prone endpoints; row-level security on every table and private buckets if any client talks to the database directly, each covered by tests; how secrets and signing keys are stored; CSP and the other security headers for the site; targets OWASP MASVS for the app and ASVS 5.0 Level 2 for the API unless SPEC.md says otherwise.
- Threat model: for each main use case, what could go wrong under STRIDE (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege), including the phone's own threats: a lost or stolen phone, a rooted or jailbroken one, another app on the same phone reading links, notifications or the clipboard, an attacker reading the unpacked app, and a script calling the API without the app. Keep the 10 most likely threats, each with its mitigation and the test that proves it.
- Privacy by design: a data-flow diagram that includes every SDK and third party and their countries; what stays on the phone; how account deletion works end to end (in the app, from the web page, in backups, at third parties, push tokens included) and how data export works. These answers become the store privacy forms in Phase 7.
- Performance and cost: the budgets from SPEC.md, measured on the slowest phone in the device list: cold start (Android vitals treats 5 seconds or more as excessive, so aim well under it), time to the first useful screen, scrolling without dropped frames, app download size, data used per session, battery (no polling in the background); caching; pagination limits; quotas on expensive or AI features; budget alerts, build minutes included.
- Backups and recovery: how much recent data we can lose and how long the backend can be down (from SPEC.md), the backup plan that meets that on our budget, an off-site copy of the database and of file storage, and how a restore gets tested.
- Releases: version and build numbering; how often we release; when a change may go over the air and when it needs a store build; the minimum supported app version and how it is raised; staged rollouts; and what we do with a bad release, given that a store build can't be rolled back (a server-side switch to turn a feature off, a fix release, an over-the-air rollback where allowed).

Part C. Build plan. Split SPEC.md into thin vertical slices in build order. Slice 1 is a walking skeleton: sign-in and one simple feature working end to end, in a preview build installed on a real iPhone and a real Android phone, against the API on a preview URL. Each slice is one GitHub Issue that a single session can finish, with acceptance criteria as Given/When/Then, the use case it serves, and labels (feature; parallel-safe when it shares no files with other open slices; native when it needs a new store build).

5. Update docs/ROADMAP.md, open one PR with the docs, and stop at the gate. Then tell me how to start Phase 3, and which accounts I must have ready for it (store accounts, the build service, the backend host).
```
