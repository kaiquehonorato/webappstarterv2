# 03 · Foundation: repo, CI, tests, security pipeline, builds
Model: Sonnet · effort medium · new session on your computer (it needs the iOS simulator and the Android emulator), after the Phase 2 ADRs are merged · raise to high if CI or the builds keep failing on setup details
Start: `claude --model sonnet --effort medium`

After this phase, every change is checked automatically (by hooks while Claude works, by CI on every pull request, by scheduled scans every week), and a preview build of the app installs on your phone from the pipeline, without signing keys ever passing through Claude.

```text
Read AGENTS.md, SPEC.md, docs/architecture.md, the ADRs in docs/adr/, docs/app-stores.md and docs/launch-checklist.md. This is Phase 3: build the foundation so every future change is checked automatically and the app builds from the pipeline. Do the steps in order. Each step is one GitHub Issue, one branch and one PR. After each PR, stop and show me the evidence (commands and their output, and which platforms each check ran on) before starting the next step.

Ask before creating accounts or adding anything paid. Never hardcode secrets; add placeholders to .env.example. You never see or handle signing keys, store passwords or store API keys: I enter them in the build service or CI myself, following your exact clicks. Before installing any dependency or SDK, confirm it exists on the official registry under that exact name, is actively maintained and widely used, and has a compatible license (MIT, Apache-2.0, BSD, ISC). List every new dependency in the PR. Tools named below are examples; use the equivalent for our stack.

Step 1. Skeleton. Create the folders from docs/architecture.md with one example feature that works through every layer (screen → hook → API client → controller → service → repository → database), including a test proving that user A cannot read user B's record. The API connects to the database with a least-privilege role; migrations use a separate one. Pin the toolchain (Node.js and pnpm, plus the Xcode, JDK and Android SDK versions the framework requires) and use the same ones in CI and in the build service. Fill in the real commands in the Issue and PR templates in .github/, and write CONTRIBUTING.md (install, run on a simulator and on a phone, test, release).
App identity, with me, before anything else: the bundle ID and application ID (reverse domain of a domain we own, e.g. com.company.app), which can never change once the app is in a store; the display name; and the development and preview variants with their own identifiers and names, so they install next to the production app and never point at production data. Write them into AGENTS.md under Project. Decide with me whether the native ios/ and android/ folders are generated from config and ignored, or committed, and record it in an ADR.
Protecting main: a private repository on GitHub Free can't use branch protection. Add a pre-push hook that refuses pushes to main, and check that docs/launch-checklist.md has the ruleset to turn on once the account moves to GitHub Pro: pull request required, CI checks required, no force push, no deletion. If the repository is public or already on Pro, give me the exact clicks now instead.

Step 2. Quality gates. Strict type checking. Formatter and linter (e.g. Biome, or ESLint with Prettier), with the framework's accessibility lint rules where they exist. A dead code and unused dependency check (e.g. Knip). Architecture rules that fail the build (e.g. dependency-cruiser): the app cannot import server code or database packages, screens call only hooks, features import each other only through index.ts, nothing imports from prototype/. The formatter, linter and dead code check skip .claude/, so the third-party skills in it stay as published. A Conventional Commits check. Pre-commit hooks (e.g. Lefthook) that format, lint staged files and scan for secrets (gitleaks). Server env vars validated at startup, so a missing one or a leftover placeholder from .env.example fails fast; app config validated at build time, with a check that fails when a value that looks like a secret is about to be compiled into the app.

Step 3. Tests. Unit tests (e.g. Jest or Vitest). Component tests for the app (e.g. React Native Testing Library). API integration tests against a real database in a container (e.g. Testcontainers). HTTP mocking only at the network boundary (e.g. MSW). End-to-end flows on a simulator and an emulator (e.g. Maestro or Detox), with fake data, one working example of each kind. An automated accessibility check where the stack has one (e.g. XCUITest's accessibility audit on iOS, Google's Accessibility Test Framework on Android), plus a manual VoiceOver and TalkBack pass listed in the release checklist. For the site, once Phase 4b creates it: end-to-end tests in a real browser (Playwright) with an axe check on every page, and screenshot comparisons run inside Playwright's Docker image so fonts render the same locally and in CI. Coverage thresholds only on services, where the business rules live.
Then make the authorization rule machine-checked, because it is the one rule in AGENTS.md that nothing currently proves. Write a test that builds the list of routes from the router itself (not from a hand-written list, which goes stale) and fails when any route that reads or writes a record has no test asserting that a signed-in non-owner gets 404 and an anonymous caller gets 401. Routes that are deliberately public go in an explicit allow-list in the test file, each with a one-line reason, so making a route public is a visible decision in a PR diff instead of an omission. Run it in the same CI job as the integration tests. Show me it working twice: once failing on a route you temporarily leave untested, once green.

Step 4. Security pipeline, in layers, so whatever one layer misses the next can catch:
- Every commit: the secret scan in the pre-commit hook.
- Every PR, required to merge: typecheck, lint, unit, component and integration tests, the API build and an app build check (e.g. a JavaScript bundle export or a debug build on Linux, so CI stays cheap), the end-to-end flows on an Android emulator and the site's browser tests with axe, the authorization tests, and the route-coverage check from Step 3. Once Phase 4 exists, the same list runs the token contrast test. Static analysis with Semgrep, plus custom rules that fail on SQL built from strings, HTML rendered without our sanitizer, eval or new Function, shell commands built from input, tokens written to non-secure storage, and WebViews with JavaScript bridges. (GitHub's CodeQL and secret scanning don't run on a private repository owned by a personal account, even on Pro. Semgrep runs only in CI and isn't shipped, so its LGPL license doesn't reach the product.) Dependency vulnerability audit covering the native dependencies too. A license check that fails on GPL, AGPL, unknown or custom licenses unless I allow-listed them. A secret scan of the diff (gitleaks). Size limits: the app's download size and JavaScript bundle (or the stack's equivalent), and each site page's JavaScript, set from the budgets in docs/architecture.md.
- Before each release, on the release build: unpack the built app (the .ipa, .apk or .aab) and scan it for secrets, internal URLs and debug flags; check the Android manifest for exported components, `debuggable`, cleartext traffic and backup settings, and Info.plist for App Transport Security exceptions and purpose strings. Optional: a static scan of the built app with MobSF (GPL-3.0, run as a tool and never shipped). Write it as a script /store-release calls.
- Security headers and cookies as code, for the API and the site: CSP (nonces when rendered on the server, hashes on a static host), HSTS, X-Content-Type-Options, frame-ancestors, Referrer-Policy, Permissions-Policy; cookies HttpOnly, Secure and SameSite; CSRF protection for cookie sessions; CORS with an explicit allow-list. One test asserts all of them on a real response.
- Supply chain: lockfiles committed and installed frozen in CI, native ones included. pnpm 11 or later, with these settings in pnpm-workspace.yaml: `minimumReleaseAge: 1440`, so a version must be a day old before it installs (written out, because then pnpm stops with an error instead of falling back to a younger version when nothing older matches); `strictDepBuilds` left on, with each install script I approve listed under `allowBuilds`; `trustPolicy: no-downgrade`. GitHub Actions pinned to commit SHAs with minimal token permissions; CI never prints env vars or runs with shell tracing, and secrets aren't available to pull requests from forks. Renovate with `config:best-practices` (it waits 3 days before proposing a new npm version and pins Actions to SHAs), or Dependabot with its cooldown, grouping updates weekly; framework upgrades get their own Issue. A software bill of materials (SBOM, e.g. CycloneDX) for the app and the API generated by the pipeline on every release build: the Cyber Resilience Act requires one from December 2027, and it is how we answer "are we affected?" when the next vulnerability in a dependency is announced.
- Every week, on a schedule: a DAST baseline scan (OWASP ZAP) against the API and the site on the preview or staging URL, signed in with a test account kept in CI secrets (without one it only scans the sign-in endpoint); a Lighthouse CI run on the site's pages; the end-to-end flows on an iOS simulator if they don't run on every PR; and a full dependency audit. Findings open GitHub Issues.
- Inside Claude Code: /security-review before any PR that touches auth, data, APIs, uploads, permissions or deep links, and a scan with the claude-security plugin before each release. Optional, in the terminal: the security-guidance plugin (docs/skills-and-plugins.md says what it costs).

Step 5. Claude Code hooks for this repo, in .claude/settings.json, merged with the existing deny and ask rules:
- Format files after each edit.
- A Stop hook script in .claude/hooks/ that runs the fast checks (typecheck, lint, unit tests of the changed package) and sends only the failures back to Claude. So it can't loop or slow down every reply: it exits at once when its input has "stop_hook_active": true (Claude is already fixing an earlier failure) or when `git status` shows no changed source files; its timeout is about 2 minutes; on failure it prints at most the last 40 lines to stderr and exits with code 2, which makes Claude fix them before it stops. Builds and device flows stay out of it: they are too slow for every reply.
Then run /run-skill-generator, or ask me to type it if you can't start it yourself, so /run and /verify know how to start the API and the app on a simulator.

Step 6. Builds, deploys and observability.
- API and site: a preview deploy for every PR, behind the host's deployment protection (sign-in required) and with fake data only; if that protection costs extra on our plan, tell me the price first. Production deploys only from main, through CI or the host's Git integration, never from a laptop. Rollback steps written down and tried once. A /health endpoint. Structured logs with a request ID, the app version and a redaction list.
- App builds: development, preview and production profiles in the build service, each with its own identifiers and API URL. Give me the clicks to create the signing credentials in the build service or CI secrets myself, and to turn on Play App Signing; you never see the keys. Preview builds go to TestFlight internal testing and Google Play's internal testing track (or the private route in docs/app-stores.md), installed on my phones as the evidence for this step. If my Google Play account is a new personal one, help me start the 14-day closed test with 12 testers now, with this preview build, so it ends long before launch.
- Over-the-air updates, if Phase 2 chose them: separate preview and production channels, updates signed, and the runtime version tied to the native code so an update never reaches a build it doesn't match.
- The forced-update path: the API's minimum supported app version (from .env.example), the typed "update required" error, and the app's update screen with a link to each store, tested against a preview build.
- Crash reporting for the app and the API that scrubs personal data (e.g. Sentry with sendDefaultPii off), with debug symbols and source maps uploaded privately from the pipeline and never shipped. Error boundaries on every screen. The success signals measured the way docs/architecture.md says.

Step 7. Docs. A README with setup in five commands or fewer for the API and one for the app on a simulator, a complete .env.example with the public app values marked, and docs/architecture.md linking every ADR.

Not now: the scale tools in the "Later" list of docs/ROADMAP.md (staging, tracing, mutation tests, load tests, a device farm, CODEOWNERS). Keep that list current, with the event that brings each one in.

Final output: a checklist of every item above marked done, or skipped with the reason; the evidence for each, with the platforms it ran on; and what I must do by hand: accounts, signing credentials, secrets, testers for the closed test, two-step sign-in on every account the project uses, and anything you added to docs/launch-checklist.md.
```

**Why it is lighter than it could be:** a solo project needs the safety net on day one (tests, scans, hooks, CI, builds from the pipeline) but not the scale tools. The "Later" list in docs/ROADMAP.md keeps them from being forgotten without paying for them early (mistake #5). iOS builds and iOS simulator runs cost the most in CI minutes, so they run before releases and weekly instead of on every PR, unless the budget allows more.
