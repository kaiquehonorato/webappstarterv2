# 01 · Prototype and illustrated use-case manual
Model: Sonnet · effort medium · new session · raise to Opus · medium if the visual directions look generic or alike
Start: `claude --model sonnet --effort medium` · have 2–3 screenshots of apps you like ready, and your phone at hand

You see the product, and hold it in your hand, before any technology is chosen: three visual directions, a clickable prototype of the main use cases that you open on your own phone, and a manual with screenshots of every step.

```text
Read AGENTS.md, SPEC.md, docs/GLOSSARY.md and docs/ROADMAP.md. This is Phase 1: show me what the app will look like before we choose any technology. Work only in prototype/ and docs/manual/. No backend, no real data, no production code, and no app framework yet: the framework is a Phase 2 decision. The prototype is static HTML, CSS and a little JavaScript, sized and styled as a phone app. The only dependency allowed is Playwright (Apache-2.0) as a dev tool inside prototype/, for screenshots.

Screenshots cost tokens each time you open one (about 450 for 390×844). Open only the style tiles and the screens you changed, and write captions from the walkthrough's steps instead of looking at every image.

Step 1. References and visual directions. First ask me for 2–3 screenshots of apps I like and one I don't, and what I like about each. Save them to prototype/references/. They are internal references only: nothing is copied from them into the product, and they go when prototype/ goes. Then use the frontend-design skill, with SPEC.md and this prompt as its brief, to propose three clearly different directions that come from the product's subject, its audience and those references, and that still feel at home on iOS and Android: the tab bar, the back navigation, sheets and system alerts stay where people expect them, and the identity lives in color, type, shape, imagery, icons and motion. For each one: a name; the idea in one sentence; a palette of 4–6 named hex colors with text contrast of 4.5:1 or more, in light and dark; a type pairing and the fonts' licenses (they must allow embedding in an app), or the system fonts on purpose; shape language (radius, borders, depth); an icon set and its license; an idea for the app icon; the one memorable element; and how motion and haptics are used.
Unless my references ask for them, avoid the looks that make generated apps interchangeable: a cream background with a serif headline and a terracotta accent; near-black with a single neon accent; identical rounded cards with the same soft grey shadow; purple-to-blue gradients; all-caps labels above every heading; "01 / 02 / 03" numbering on content that isn't a sequence; one italic or colored word in each headline; an arrow on every button; a default font because it is the default.
Render each direction as the same key screen (a style tile) in prototype/directions/. Take screenshots with Playwright's iPhone and Pixel device profiles, save them to docs/manual/img/directions/, show them to me and ask me to pick one or combine parts. If the /design command is available in this session you may draft the directions there instead and export the PNGs to the same folder.

Step 2. Clickable prototype. Build the top use cases from SPEC.md in the chosen direction with the simplest tools: static HTML, one CSS file holding the design tokens, and a little JavaScript. Make it behave like an app: a fixed tab bar or the navigation SPEC.md implies, a back control on pushed screens, sheets and confirmation dialogs where the flows need them, safe-area padding, and a web app manifest with `display: standalone` so it opens full screen from my home screen. Use realistic fake data in the users' language. Every main screen has its loading, empty, error, offline and success states, and the flows include the dialogs they need: the screen that explains a permission before the system asks for it, a confirmation that names what will be lost before a destructive action, undo after quick actions, form errors that say how to fix the problem, and search or suggestions where they save the user time. Touch targets of at least 44×44 px. It must stay usable with the browser's text size at 200% and with a screen reader. Copy follows docs/writing-style.md and uses the words in docs/GLOSSARY.md.
Then tell me how to open it on my phone: a one-line command that serves prototype/ on my local network (for example `python3 -m http.server` bound to my computer's address, on a network I trust), the URL to type on the phone, and how to add it to the home screen.

Step 3. Illustrated use-case manual. Write a Playwright walkthrough in prototype/manual/ that follows each use case step by step with the iPhone device profile and saves screenshots to docs/manual/img/<use-case>/, adding the Pixel profile only for screens that differ. Then write docs/manual/USE-CASES.md. For each use case: the goal, who does it, numbered steps each with its screenshot and a one-line caption, which permissions it asks for and when, and what the person sees when something goes wrong or the connection drops, and how they recover. Write it for a non-technical reader.

Step 4. Review together. Run an automated accessibility check (axe) on each screen, and check the touch targets and the 200% text size. Ask me what I noticed using it on my own phone. List what the walkthrough revealed: missing states, confusing steps, permissions asked at the wrong moment, things the spec didn't cover, accessibility problems. Propose changes to SPEC.md and apply only the ones I approve.

Step 5. Gate. Write prototype/README.md saying this folder is throwaway and the app must never import from it. Record the chosen direction in an ADR with links to its screenshots. Update docs/ROADMAP.md, open the PR, and wait for my approval. Then tell me how to start Phase 2.
```

**Why a throwaway prototype in HTML:** it is the cheapest way to find wrong assumptions, it needs no framework decision, and it runs on your phone in a minute. Keeping it separate stops demo code from becoming production code without tests (mistake #4 in docs/vibe-coding-mistakes.md). Phase 8 regenerates the manual from the real app on iOS and Android with the `/use-case-manual` steps.

**Tips**
- Use the prototype on your phone for a day: in the bus, with one hand, in sunlight. That finds more problems than any review on a laptop.
- If the three directions look generic or alike, redo only Step 1 in a new session on Opus at medium effort.
- For small visual fixes (spacing, a color, a font size), where `/design` is available, edit its mockup yourself and ask Claude to match it. One edited mockup costs fewer tokens than several rounds of "a bit rounder, a bit slower".
