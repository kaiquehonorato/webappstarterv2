# 06 · Security audit
Model: Opus · effort high; max for the deep scan before launch and after changes to sign-in, payments or data access (or Fable if your plan has it) · fresh session, not the one that wrote the code · every 3–5 features and before launch
Start: `claude --model opus --effort high`

Automated scanners run first, including a scan of the built app, then a manual review of 103 checks: 83 for the backend, the store pages and operations, mapped to OWASP Top 10:2025, and 20 for the app on the phone, mapped to OWASP MASVS 2.1 and the Mobile Top 10 (2024). They include every item of the common 50-point checklist for AI-built apps; docs/security-model.md maps each one. Nothing is marked safe without evidence. Some security requests on Opus 5.5 and Fable can be moved to a fallback model by Anthropic's safety classifiers; that is expected and the audit continues.

Remember that an attacker has the app too: they can unpack it, run it on a rooted phone, and call the API without it.
Don't change code during the audit. Never mark an item SAFE without evidence (file:line, a test, or a command and its output). Mark N/A when it doesn't apply and UNKNOWN when you can't verify it.

Step 0. Automated sweep. Run and collect the results of: the CI security jobs (static analysis, dependency audit including native dependencies, license check); the package manager's outdated report and the framework's upgrade status; a secret scan of the full git history, of the site's built bundle and of the built app (the pre-release script from Phase 3: unpack the .ipa, .apk or .aab, scan for secrets, internal URLs and debug flags, and read the Android manifest and Info.plist); with my OK, a capture of the app's network traffic on a test build through a proxy, listing every host it contacts and what it sends, to compare with the store privacy forms (test builds only: production builds don't trust a proxy's certificate); a static scan of the built app with MobSF if we set it up; requests for /.env, /.git/config and .map files against the preview and production URLs of the API and the site; the database provider's security advisor (for Supabase, the Security Advisor), if we use one; a Claude Security scan of the whole codebase at high effort, if the plugin is installed; and, with my OK, a DAST baseline scan (OWASP ZAP) against the preview URL, signed in with the host's bypass token or a test account so it reaches the app behind the sign-in page. **The deeper hunt, before launch.** The checklist above gives breadth: 103 named checks, each marked with evidence. What it cannot do is find the problem nobody thought to put on a list. For that the kit carries Cloudflare's `security-audit` skill in `.claude/skills/security-audit/`, the skill that seeded their own vulnerability discovery harness. It works the other way round: it maps your trust boundaries, sends an isolated hunter at each one, then hands every candidate to a fresh agent whose job is to disprove it. Its guide to desktop, mobile and local IPC covers the boundaries between the app and the rest of the phone. Nothing becomes a finding without a named boundary, a defeated control and an observed result, and only confirmed findings get a severity.

Run it after the checklist audit passes, in its own session, and say which method is in charge:

```text
Use the security-audit skill to audit this codebase. Profile: quick. Budget: 25 agent invocations. Write the report to ~/audits/<repo-name>/run-1, outside this repository. This is my own repository and I authorize the review. Source review only: do not probe any deployed URL, and do not execute target code unless every sandbox control the skill requires is available. Follow the skill's own method, not the 103 checks in prompts/06-security-audit.md, which I have already run. Change no code.
```

What to expect. It spends agents, so set the budget before you start: roughly one hunter per coverage unit and one or two verifiers per candidate. `quick` is the right profile for a first app, and `standard` and `deep` cost several times more. It stays source-only unless you give it an operating-system sandbox with no network and hard resource limits, and it says so instead of guessing, so the scans against the preview URL in Step 0 stay the kit's job. It writes `findings.json` against a schema, checked by its two Node validators, plus `REPORT.md` and `NEEDS-VALIDATION.md`. `needs_validation` is not a weak vulnerability: it means the deciding fact lives outside the code, and the record names that fact. Cloudflare measured one run finding about half of what repeated runs found together, so one pass is not a clean bill of health.
