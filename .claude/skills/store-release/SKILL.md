---
name: store-release
description: Prepare and ship one app release - version numbers, store build or over-the-air update, test builds on real devices, store forms, submission after approval, staged rollout and watching it.
disable-model-invocation: true
argument-hint: "[version, e.g. 1.4.0]"
---
Prepare release $ARGUMENTS, following AGENTS.md, SECURITY.md and docs/app-stores.md. You prepare; I approve every step that reaches users. Never submit, change a rollout or publish an update without my explicit OK in this session.

1. **What is in it**: list the merged PRs since the last release tag and sort them: changes that need a new store build (native code, SDKs, permissions, entitlements, app config, icons, splash, the framework's runtime version) and changes that could ship over the air (JavaScript and assets only, compatible with the installed runtime). Any change in the first group makes this a store release. An over-the-air update is allowed only for fixes and changes the store already reviewed the app for (docs/app-stores.md), never for a new feature that changes what the app does.
2. **Ready to ship?** main is green; the last security audit has no open Critical or High finding; nothing in docs/launch-checklist.md went stale. If the release adds a permission, an SDK, a new kind of data or a new purpose, the store privacy forms and the data inventory in SPEC.md must change first: draft the new answers for Apple's privacy labels and Google's Data safety form and wait for me. Same for the age rating questionnaires if content changed.
3. **Numbers**: the version follows semver and is $ARGUMENTS on both platforms; the build number goes up on both (it must be higher than every build ever uploaded). Write "What's new" in each store language, specific and short (docs/writing-style.md). Commit on a release branch and open a PR.
4. **Build**: after the PR merges, build with the pipeline's production profile, never from a laptop. Confirm the build used production config: production API URL, release flags, no debug menu, crash reporting on with personal data scrubbed, symbols uploaded privately. Run the check from Phase 6 Step 0 on the built files: secrets, debug flags, exported components, cleartext and backup settings.
5. **Test builds on real devices**: upload to TestFlight and to Google Play's internal testing track (or the private channel docs/app-stores.md describes for internal apps). Give me a short device checklist: install over the previous version (data survives, the user stays signed in); a fresh install; the release's changed flows on one iPhone and one low-end Android phone; offline and slow network; the forced-update screen against a test minimum version; sign-in, sign-out and account deletion. Wait for my results.
6. **Store listing**: new screenshots only where screens changed, at the sizes each store asks for; review notes that tell the reviewer how to reach every new feature, with the demo account (credentials go in the store form, never in the repo).
7. **Submit**: after my OK, give me the exact clicks or run the submit command I approve. Choose a phased release on the App Store and a staged rollout on Google Play, starting small, unless I decide otherwise.
8. **Watch the rollout**: for 48 hours, compare crash-free users, ANRs, errors, sign-in failures and support messages with the previous version. Stop condition, agreed with me before submitting: the rate at which we pause the rollout. Pausing a rollout stops new installs, but people who already updated keep this version, so a bad release needs a fix release, not only a pause.
9. **Over-the-air path** (only when step 1 allowed it): publish to the preview channel, check it on both platforms, then publish to production after my OK, with the rollback command written down before publishing.
10. **Close**: tag the release in git (`v$ARGUMENTS`), update docs/ROADMAP.md and the release notes, and, when a security fix or breaking API change requires it, propose raising the minimum supported app version once this release is live in both stores.
